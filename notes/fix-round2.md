## `auv_capture_state` (12th tool)

Params are the same targets as `auv_wait_for_change`: `window_id`,
`application_id`, `display_id`, `region`.

- Captures one LOGICAL frame of the target, then fetches a downscaled RGBA
  image with `runner.captures.image(frame, { encoding: ImageEncoding.RGBA,
  maxSize: { width: 320, height: 320 } })`.
- Stores `{ width, height, data: Uint8Array copy, hash, mode, targetKey,
  target, capturedAt }` in a module-level store: **LRU max 20 entries, TTL
  5 minutes**. `data` is copied so the store does not alias SDK buffers.
  Nothing is written to disk.
- Returns `{ command_id: 'frame.captureState', state_token: randomUUID(),
  hash, width, height, mode, captured_at: ISO-8601, daemon_mode,
  daemon_endpoint, warnings }`.
- The store also keeps the target plan, so `auv_wait_for_change({
  state_token })` can re-capture the same window/display/region even when the
  wait call passes no target params. If both a token and an explicit target are
  passed and they differ, the stored target is used and a warning says so.
- `requireCaptureState(token)` is a transport-free lookup used by the tool
  body, so an unknown/expired token fails with a clear `AuvError`
  (`AUV_STATE_TOKEN_INVALID`, "Call auv_capture_state again…") **before** any
  daemon attach/start.

## `auv_wait_for_change` rework

Params added: `state_token?`, `min_changed_ratio?` (number 0–1, default
`0.01`), `pixel_threshold?` (integer 0–255, default `24`). `baseline_hash` is
kept as a legacy input. `interval_ms` 50–5000 and `timeout_ms` 100–120000 are
unchanged.

Baseline resolution order:

1. `state_token` — use the stored RGBA pixels/hash (`baseline_source:
   'state_token'`, pixel comparison).
2. `baseline_hash` — legacy ThumbHash-only comparison (`baseline_source:
   'provided'`, `comparison: 'hash'`), with the warning
   "Compared ThumbHash only; pass state_token for pixel-ratio comparison."
3. Otherwise capture a fresh baseline at call start (`baseline_source:
   'captured'`, pixel comparison).

Pixel comparison (state_token/captured paths):

```
changed_ratio = pixels where |R1-R2| > T or |G1-G2| > T or |B1-B2| > T
                / total pixels
changed       = changed_ratio > 0 and changed_ratio >= min_changed_ratio
```

Alpha is ignored (button/cursor flicker is usually an alpha/antialias change,
and RGB-only counting matches the requested rule). The pixels come from the
same `maxSize {320,320}` downscale for the baseline and every poll, so the
ratio is resolution-independent and cheaper than full frames. A dimension
change (window resize/aspect change) is treated as fully changed
(`changed_ratio: 1`) with a warning.

Returned value keeps the old fields and adds the comparison details:

```
{ result: 'changed'|'no_effect'|'timeout', changed, changed_ratio,
  min_changed_ratio, pixel_threshold, elapsed_ms, before_hash, after_hash,
  baseline_source, comparison: 'pixels'|'hash', mode, timeout_ms, interval_ms,
  artifact_path: null, warnings }
```

`no_effect` still means the caller's signal aborted before the deadline
without a change; `timeout` means the deadline was reached. No files are
written. The timeout warning includes the last observed ratio, e.g.
"No change above min_changed_ratio 0.01 within 800 ms (last changed ratio
0.0000)."

## `auv_click` x/y `space`

New optional `space` enum `window|screen|display` for x/y clicks:

| space | Meaning | SDK call |
| --- | --- | --- |
| `window` | window-local point; default when `window_id`/`application_id` is given | `WindowClient.click({x,y})` |
| `screen` | logical screen point; default otherwise (and when only `display_id` is given) | `runner.input.click(Position.screen(x,y))` — foreground global click, no window target |
| `display` | display-local point; requires `display_id` | `runner.input.click(Position.display(display_id,x,y))` |

- `space: 'screen'` with a `window_id`/`application_id` is the Unity/Canvas
  workaround: the click is delivered as a real foreground screen click while
  the result still reports `window_point` (converted with the window frame) for
  diagnostics.
- `space: 'display'` was confirmed straightforward (`Position.display` exists
  and works), so it is implemented rather than rejected.
- With `display_id` and no `space`, the default is screen (per the Lead's
  requested default); the result still reports `display_point` when the display
  frame is known.
- Text/OCR clicks reject `space` (they use the matched bounds). The result
  includes `space`, `screen_point`, `window_point` and `display_point`.
- The tool description now recommends `space: 'screen'` (or omitting
  `window_id`) for Unity/Canvas apps.

## Risks / notes

- `auv_capture_state` and the RGBA fetch are read-only but add one capture +
  one image RPC (and up to ~410 kB of pixels) per call. The downscale at 320
  keeps the per-poll fetch small.
- Pixel comparison still counts real UI animation as a change: capture the
  state immediately before the action and use `min_changed_ratio` to ignore
  small rendering/focus flicker. For a "did the story advance" question,
  compare the state token captured *after* the action too if needed.
- The store is per Host process, in memory: a plugin reload or Host restart
  invalidates tokens; TTL is 5 minutes and only 20 states are retained (older
  tokens fail with the clear re-capture error).
- `baseline_hash` is deliberately coarse (ThumbHash only) and warns; use
  `state_token` for the pixel ratio. Its change ratio is reported as 1/0.
- `space:'screen'` with a window target resolves the window once to report
  `window_point`; that read never affects delivery.
- `display_id` without `space` now defaults to screen coordinates (Lead's
  requested default); pass `space:'display'` for display-local points.
- `auv_keys` Space in Unity remains an upstream AUV delivery issue; the plugin
  keeps the Lead's foreground-delivery path and the "delivery is not proof of
  reaction" warning. Use `auv_capture_state`/`auv_wait_for_change` to check
  whether a key had any effect.
