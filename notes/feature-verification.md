## Coordinate model

All tool points are **logical screen points** unless a call documents
window/display space. The formula shown in screenshot/OCR/click/scroll/drag
values (and in the tool descriptions) is:

```
image_pixel  = (screen_point - capture.bounds.origin) * pixel_ratio
pixel_ratio  = capture.pixel_size.width / capture.bounds.width
             (= scale_factor when the capture is LOGICAL)
window_point = screen_point - window.frame.origin
screen_point = window_point + window.frame.origin
screen_point = display_point + display.frame.origin
```

- `auv_screenshot` values now add `bounds` (mapped `{origin,size}`),
  `origin`, `scale_factor`, `pixel_size` and `coordinate_note`; every existing
  field (`artifact_path`, `width`, `height`, `result`, `artifacts`, …) is kept.
- `auv_ocr` matches keep `bounds` and add `screen_point` (bounds center),
  `image_pixel`, `window_point` (window targets only; `null` otherwise),
  `scale_factor` and `pixel_ratio`. The OCR value also carries
  `coordinate_note`.
- `auv_click` returns `screen_point` and (window target) `window_point`;
  x/y display clicks also return `display_point`.
- `auv_scroll` returns `window_point` and `screen_point`.
- `auv_drag` returns `from`/`to` (input space), `screen_start`/`screen_end`,
  `screen_point` (delivered end), `window_point`/`window_start`/`window_end`
  for window targets, and `display_start`/`display_end` for display targets.

A real observation from the read-only smoke: `display.capture` (LOGICAL)
reported `scale_factor: 1` with a 1728×1117 capture, while
`display.findText`'s internal capture reported `scaleFactor: 2` and
`image_pixel` = `(screen_point) * 2`. So `image_pixel` is relative to the
capture that produced the match, not necessarily to the screenshot artifact.
`pixel_ratio` makes that explicit.

## `auv_drag`

Params: `from`/`to` `{x,y}` (required), `space` `screen|window|display`,
`window_id?`, `application_id?`, `display_id?`, `button?`
`left|right|middle` (default left), `duration_ms?` 0–30000 (default 300),
`activate?`, `allow_repeat?`.

- `space` is inferred when omitted: window for `window_id`/`application_id`,
  display for `display_id`, screen otherwise. Explicit `space: 'window'`
  requires a window target, `space: 'display'` requires `display_id`, and
  `display_id` is rejected outside display space.
- Window points are converted with `client.window.frame`; display points with
  `runner.displays.list()`'s matching display frame. For window/app targets the
  target is focused first when `activate` is true (default for targets); the
  frame is refreshed after activation before conversion. Reason (in code
  comments): macOS drags move the real pointer and an inactive window can
  consume the first press.
- The request is AUV's CLI straight-line construction:
  `runner.input.dragMouse({ movement, button })` where `movement.start` is a
  `point` screen source, `curve.segments` is one cubic Bézier
  `{control1: {dx/3,dy/3}, control2: {2dx/3,2dy/3}, end: {dx,dy}}`, options are
  `{duration: duration_ms, sampleRateHz: 60, curveTolerance: 0.5}`, and no
  target is set (foreground delivery).
- Verified offline through the **real SDK method wrapper and generated
  Protobuf schema** against an in-memory mock transport (`createMockTransport`
  + `InputService.dragMouse` handler): the serialized request is
  `DragMouseRequest { button: 1, movement: { start: point(100,200), curve:
  [control1(100,50), control2(200,100), end(300,150)], options:
  {sampleRateHz:60, curveTolerance:0.5, duration:{seconds:0n,nanos:300000000}}
  }, no target }`. The number `duration` is converted by the SDK to a
  `google.protobuf.Duration` automatically. No daemon or input was involved.
- Risk: the live drag branch was not exercised (would deliver real input).
  Request shape, curve and coordinate conversion are covered by the mock/fake
  checks; actual Runner behaviour on macOS (focus/activation timing, drag
  duration) remains a smoke-test item for a human-approved run.

## `auv_wait_for_change`

Params: `window_id?`, `application_id?`, `display_id?`, `region?`,
`timeout_ms?` 100–120000 (default 5000), `interval_ms?` 50–5000 (default 200).

- Captures a baseline frame of the target with `window.capture` /
  `displays.captureRegion(region, selector?)` / `displays.capture`.
- Polls every `interval_ms`; compares `CapturedFrame.thumbhash` bytes as
  `thumbhash:<hex>`. When a frame has no ThumbHash it falls back to
  `sha256` of `runner.captures.image(frame, {encoding: WEBP, maxSize:
  {width: 512, height: 512}}).data` and adds a warning.
- Returns `{status: 'completed', command_id: 'frame.waitForChange', result:
  'changed'|'timeout'|'no_effect', changed, elapsed_ms, before_hash,
  after_hash, mode, timeout_ms, interval_ms, artifact_path: null, warnings}`.
  `timeout` = deadline reached with no change; `no_effect` = the caller's
  signal aborted before the deadline with no change; `changed` = a later hash
  differed. No files are written.
- `region` is only valid for screen/display targets; `window_id`/
  `application_id` and `region` are mutually exclusive, and `region` +
  `display_id` captures that region of the display.
- Live read-only smoke: a 30×22 menu-bar region (known static) returned
  `result: timeout, changed: false, elapsed_ms: 727, artifact_path: null`
  (baseline/after thumbhashes identical). A window capture of an animating
  window returned `changed: true, mode: 'window'` in 596 ms, and an earlier
  region inside an app window returned `changed: true` too. All are expected
  behaviours; `changed` proves frame motion, not that a previous input caused
  it, so use a known-static target when checking for effects.

## `auv_keys` policy/focus

New params: `policy?` `background-only|background-preferred|foreground-preferred`,
`focus?` boolean, `allow_repeat?`.

- Defaults: `focus` = true when a window/application target is given, false
  otherwise; policy = `foreground-preferred` in both cases. Background
  policies are rejected without a target (AUV cannot deliver background
  keyboard input to the foreground app), and `focus: true` without a target is
  rejected.
- With a target and `focus` true: `window.setFocus()` for `window_id`,
  `applications.activate({applicationId})` for `application_id`, then
  `client.pressKeys(keys, {count, interval, policy})`. Without a target:
  `runner.input.pressKeys` with the `foreground` recipient and
  `foreground-preferred` policy (`count`/`interval` unchanged from 0.1.1).
- `focus: false` only skips the explicit focus RPC; AUV's
  `WindowClient.pressKeys` can still bring the window forward when the policy
  is `foreground-preferred` (the default). Set a background policy as well for
  non-activating delivery. With `application_id`, activation happens through
  `applications.activate`; keys are then delivered through the resolved main
  window client.
- The result records `policy`, `focus`, `focus_target`, `focus_evidence` and the
  normalized SDK action. Every successful call adds the warning
  `AUV confirms key delivery only; it does not prove the app reacted. Pair
  auv_keys with auv_wait_for_change (or a fresh auv_screenshot) to verify the
  effect.` The tool description says the same and suggests
  `auv_wait_for_change`.

## Repeat guard (mutating tools)

Applies to `auv_click`, `auv_type`, `auv_keys`, `auv_scroll`, `auv_drag`.
Each call is identified by tool name + canonical JSON of the parsed plan
(sorted object keys; `allow_repeat`/`allowRepeat` ignored on purpose).

- Calls 1 and 2 of an identical call inside 30 s execute normally; the 3rd
  (and further identical calls) are **not executed** and return
  `{status: 'no_effect_repeat', blocked: true, tool, repeat_count,
  repeat_window_ms: 30000, message, warnings}`. The message is: “Same call
  repeated without a change; take a new screenshot and re-locate before trying
  again. Pass allow_repeat:true to send it anyway.”
- A different call, a gap longer than 30 s, or `allow_repeat: true` resets the
  state. `allow_repeat: true` executes the call and clears the guard.
- `failure` validation happens first: malformed calls throw their normal
  parameter errors and never consume guard budget.
- The guard is module-level state in the Host process (shared by all
  registrations of `createTools()`); a plugin reload resets it. DSH's own
  repeat reminder is separate and unchanged.
- Unit coverage: key canonicalization (order independence, `allow_repeat`
  ignored), 3rd-call block, stay-blocked, bypass, different-call reset, 30 s
  expiry, message content, and blocked-value rendering.

## SDK/API surprises worth recording

1. `runner.input.dragMouse` accepts the `MoveMouseRequest` init shape from the
   types, and the SDK converts a numeric `options.duration` (ms) to
   `google.protobuf.Duration` at any depth. Verified through the real SDK with
   the in-memory mock transport.
2. `DragMouseRequest.movement` has no `curve.start`; the CLI/our builder only
   sets `movement.start.source`. The mock serialization confirms the field
   names.
3. No SDK drag `target` means foreground delivery (documented in the proto
   comments); window/display drags are therefore delivered as foreground
   screen gestures after activation/conversion.
4. `WindowClient.window.frame` is a snapshot; after `setFocus()` a
   `client.refresh()` is needed to convert with the current frame.
5. `findText` responses can have a different capture scale than
   `displays.capture(LOGICAL)` (observed `scaleFactor: 2` vs `1`), so
   `image_pixel` must use the findText capture metadata — hence per-match
   `pixel_ratio`.
6. `ThumbHash` is a `Uint8Array` on every `CapturedFrame` observed; the WEBP
   hash fallback is implemented but untested live because the runner always
   supplied a ThumbHash.
7. A live `auv_wait_for_change` on an animating window can legitimately return
   `changed: true` quickly (observed when polling an app window's content);
   pair the tool with a known-static region/window (menu-bar/desktop regions
   timed out consistently) when checking for input effects, or compare
   before/after state another way.

## Remaining risks

- Live `auv_drag` (real pointer movement, button hold, focus timing) is not
  exercised by design. Request shape and conversion are validated against the
  real SDK schema; a human-approved drag smoke test is still recommended.
- Drag delivery is foreground-only; a running app may intercept the gesture
  differently than the CLI (the CLI also builds the same foreground request,
  so this should match). `activate: false` skips only the explicit focus RPC;
  the real pointer gesture can still raise whatever window is under the cursor.
- `wait_for_change` `no_effect` (`AbortSignal` before deadline) is unit-tested
  but not reachable from a normal tool call unless the Host aborts the tool.
- Repeat guard state is per Host process, so an external caller and DSH share
  the same counter; it deliberately refreshes on blocked calls (a persistent
  model cannot poll forever), and `allow_repeat` clears it.
- `dist/index.mjs` was regenerated locally by `pnpm build`. It is gitignored
  build output (the release workflow builds it), so nothing under `dist` is
  tracked; a local build is required for `node tools/check-tools.mjs` to see
  the 11-tool bundle. The Lead can rerun `pnpm build` before release.
- Version remains 0.1.1; bump to 0.2.0 (package.json + release notes) is the
  Lead's call.
